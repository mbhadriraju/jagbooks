# Architecture

FastAPI owns Supabase Auth validation, Data API operations, Storage transport, Groq extraction, and XLSX processing. Next.js provides the workbook preview, Analysis, and source review. A same-origin finance route forwards browser bearers through a private Vercel service binding. Vercel injects the binding into Next.js automatically. The deployment exposes a single public origin. Backend contains a self-contained copy/adaptation of the root inference rules and workbook layout; it never imports root scripts or writes root prototype files.

Each authenticated request validates its Supabase Auth bearer JWT and forwards it with the publishable API key to Data API/Storage. RLS uses operator-controlled `finance_members`, tied to `auth.users`. Runtime has no service-role key. Google social sign-in uses Supabase’s `/auth/v1/callback`, followed by the app-side PKCE callback/code exchange; the browser SDK handles that exchange and session refresh. `GET /auth/providers` reads live public Auth settings without a user bearer, while `/auth/access` separately reports finance membership for a verified user. Provider enablement alone never grants group access. Optional callback configuration must match the same project, and anonymous Auth users are rejected. Auth identity/access responses use private/no-store caching. Composite foreign keys prevent crossing sheets/groups with source files, workbook objects, history, or head pointers.

## Source ingestion

`finance_files` owns immutable source metadata. Bytes use private `bvw-finance-files/<group>/<file>/source`. Bounded streamed uploads verify MIME signatures and checksum identity. Duplicate bytes within a logical sheet reuse metadata. An interrupted upload retains its uploading record; retry can reconcile already-stored bytes before completing metadata state.

The UI upload stages the original and navigates to source review. The review endpoint extracts the stored source and computes the cell delta using the same mapping and validation as application. Confirmation publishes against the exact reviewed head UUID. The default API upload still attempts extraction and rolling workbook application immediately. Groq reads stored bytes after checksum verification. Text PDFs use PyMuPDF and images use a configurable vision model. Both use the prototype's accounting rules, six classes, 33 categories, and six transaction fields. The default models use Groq's strict JSON schema. Other configured models use JSON object mode with the same schema in the prompt. The backend validates the entire response, rejects truncation, and converts source references and decimal dollar amounts to draft references and exact integer cents. `finance_finish_extraction` locks the file and atomically saves draft audit rows, an immutable `finance_extractions.rows` batch, and processed status. Concurrent completions cannot duplicate rows. Expensive Groq calls can still duplicate before the lock. Processing is synchronous.

Processed means extracted, not necessarily applied. A batch with unknown required fields or dates outside workbook months cannot update the workbook. Source/extraction remain available. File listings expose `applied_to_current_workbook` independently of processed status.

## Rolling workbook

`finance_sheets.current_workbook_id` references `finance_workbook_revisions`. Each revision records object ID, monotonically increasing version, parent, operation, optional source/restore target, applied source IDs, and derived summary. Workbook bytes use a separate private bucket, `bvw-finance-workbooks/<group>/<sheet>/versions/<object>.xlsx`. `finance_workbook_objects` stores immutable path/checksum/size metadata before byte upload, enabling scoped Storage RLS. No overwrite/upsert/delete policy exists.

A candidate workbook is built in memory from the actual current bytes, preserving existing manual edits, tables, styles and formulas. Category/month batches add integer cents to numeric cells rather than replace prior totals. Bank Deposits uses the Balance Sheet's input row to preserve Cash Flow's linked formula. All batch fields/months are validated before publishing; no partial workbook is published. The packaged template and opening balances are preserved. Formulas are left for Excel/LibreOffice to recalculate; graph summaries read numeric category inputs rather than formula caches.

`finance_commit_workbook` locks the logical sheet, checks expected head, verifies the staged Storage object exists, inserts the next revision, then changes current pointer in one transaction. Failed uploads cannot publish. A stale writer gets a conflict; document additions can reload current and rebase up to three times using cached extraction. Uploads are immutable, so losing a race may leave private uncommitted staging objects; cleanup is an explicit future operator task.

Source application is once per active lineage. A duplicate source already in the head returns current without another addition. Manual replacement retains those IDs. Restore creates a new revision pointing to the historical target's exact immutable object and copies its summary/applied IDs. Existing later revisions stay available; new uploads start from restored contents. A source excluded by restore can be explicitly reapplied from cached extraction.

Manual XLSX replacement requires the UUID of the version the user downloaded. Missing precondition returns 428; stale precondition returns 409. Validation keeps tabs, table references, labels, dimensions, months, and formula locations unchanged; numeric inputs may change. The uploaded bytes become the exact new workbook object. Restore also requires expected current UUID. Download returns the revision UUID in ETag and X-Workbook-Version headers and disables caching.

## Authority and compatibility

Current workbook bytes are authoritative for the financial spreadsheet and graph summaries. Extraction/audit transactions remain a separate provenance/review ledger; editing them does not silently rebuild a manually corrected workbook. Browser source uploads require confirmation before publishing. The existing automatic API can publish complete AI classifications without browser review. Transaction-only snapshots from the previous backend remain downloadable; new version APIs use full workbook revisions, and restore accepts only those revisions.

`finance_summary` and `finance_snapshot` remain legacy database functions for audit-ledger compatibility. Active summary reads the current workbook revision's validated numeric-input summary, which changes with manual replacement/restore. It excludes transfers/assets/liabilities/purchase orders from operating totals.

Migrations run through Supabase MCP, not requests/imports/builds. Builds validate environment configuration only. Reads are uncached. Logs contain approved route templates, safe correlation IDs, statuses, durations, and exception types; never credentials, financial bodies, raw provider text, signed URLs, or object paths.
